## 简答题

#### 主线程退出与资源回收

1、主线程（0 号线程）退出时，需要回收哪些资源？其他线程的 TaskControlBlock 可能在哪些位置被引用，分别应如何处理？

主线程退出代表整个进程退出，需要停止该进程的所有线程。线程私有资源包括用户栈、TrapContext 对应的映射和物理页、TID，以及 TCB 持有的内核栈。进程还需要释放代码、数据、堆等共享用户内存，关闭文件描述符，并清理同步对象和相关管理状态。关闭 fd 只是释放本进程的文件引用；若其他进程仍引用同一文件对象，底层对象应继续存在。页表等资源则按 MemorySet 的所有权，在相应对象最终销毁时释放。

回收时不能只清空 PCB 中的 tasks。TCB 使用 Arc 管理，只要其他位置还持有强引用，就不会自动销毁；有些引用还可能让已退出的线程再次进入就绪队列。

| 引用位置 | 处理方式与原因 |
| --- | --- |
| PCB 的 tasks 向量 | 先取出各线程的 TaskUserRes 进行清理，再移除 TCB 引用；其他 Arc 仍存在时，TCB 不会立即销毁 |
| TaskManager 的就绪队列 | 主动移除退出进程的线程，避免继续调度已失效的用户上下文 |
| 定时器堆 | 主动取消对应定时器，避免到期后再次唤醒退出线程，同时释放定时器保存的 Arc |
| mutex、semaphore、condvar 的等待队列 | 清理等待者引用；本框架的同步对象属于单个进程，可随 PCB 最终销毁而释放，但若对象仍有额外强引用，就需要保证这些引用和等待队列也能被清理 |
| Processor.current 及内核临时引用 | 退出路径需要取走当前任务引用，避免遗留临时强引用；本实验为单核，主线程退出时其他线程不会同时在另一个 CPU 上运行 |
| TaskManager.stop_task | 有意延迟释放正在退出的主线程，保证当前仍在使用的内核栈不会提前回收；下一次保存停止任务时，可替换已经停止的旧任务 |

源码中的 exit_current_and_run_next 会从处理器取走当前任务，移除进程的 PID 查询映射，并把子进程交给 INITPROC 管理。随后遍历该进程的线程，通过 remove_inactive_task 清理就绪队列和定时器，再取出线程的 TaskUserRes。清理 TaskUserRes 时会再次访问 PCB，因此先收集这些对象、释放 process_inner 的借用，再集中销毁，避免重复可变借用。

线程的用户资源需要先于整个用户地址空间释放，否则后续 TaskUserRes 的 Drop 还会重复尝试解除映射。共享用户内存、fd_table 和 tasks 随后清理。已经退出的 PCB 可以作为僵尸保留退出码，等待父进程回收；这部分管理信息的保留与继续运行用户线程是两件事。

对于正在执行退出代码的主线程，还不能立刻释放它自己的内核栈。当前框架通过 stop_task 保留一个 TCB 引用，等上下文切换完成、旧栈不再使用后再释放。其他已经停止且不再被引用的线程，其内核栈可随 TCB 销毁而回收。

#### 两种 Mutex 实现的区别

2、题目中的 Mutex1 与 Mutex2 有什么区别？这些区别可能导致什么问题？

Mutex1 采用“释放锁后唤醒，醒来再竞争”的方式。unlock 先把 locked 设为 false，再唤醒一个等待者；lock 使用循环，因此线程醒来后会重新检查 locked。唤醒只表示可以继续竞争，并不表示已经获得锁。

这种实现中，等待者被唤醒但尚未运行时，新到达的线程可能先取得锁。等待者发现锁再次被占用，就重新进入队列。因此即使等待队列是 FIFO，也不能保证最终获得锁的顺序；竞争激烈时可能出现反复睡眠、额外切换甚至饥饿。不过，只要保留循环检查，正常配对的 Mutex1 仍可保证互斥。

Mutex2 采用“直接移交”的方式。有等待者时，unlock 唤醒队首线程，并保持 locked 为 true，相当于把锁交给这个线程。被唤醒的线程从 lock 的阻塞位置返回时就视为持有锁，因此不再循环竞争。没有等待者时才把 locked 设为 false。当前框架的 MutexBlocking 就采用这种方式。

直接移交使新到达的线程不能在移交过程中抢走锁，减少了插队和重复入队。但它依赖严格的唤醒约定：从该锁等待队列唤醒的线程必须确实获得锁。如果允许无关唤醒，线程又不重新检查，就可能在没有获得锁时进入临界区。被选中的等待者迟迟不运行时，锁也会暂时留给它，其他线程即使已就绪也不能抢占这把锁。

两种 lock 与 unlock 的策略必须配套。如果把 Mutex2 的不循环 lock 与 Mutex1 的先清除 locked 的 unlock 混用，新线程可能先抢到锁，随后旧等待者也直接返回，破坏互斥。反过来，如果使用 Mutex1 的循环 lock，却让 unlock 像 Mutex2 一样保持 locked 为 true，获得移交机会的线程又会把自己放回等待队列，可能造成死锁。

## 实现与测试说明

本次为每个进程维护独立的检测开关和两份 DeadlockDetector。线程编号对应矩阵的行，资源编号对应列；mutex 的初始可用数量为 1，semaphore 使用创建时的 res_count。开关只控制是否执行安全性判断，资源记录持续维护，以支持先使用资源、后开启检测。

申请时先增加 need，开启检测后运行 is_safe。该方法复制 available 为 work，反复选择未完成且申请可满足的线程，模拟其完成后归还 allocation。全部线程均可完成才接受请求；否则撤回本次 need 增量，返回 -0xDEAD。真正的 lock 或 down 可能阻塞，因此在进入它们之前释放进程内部借用，成功返回后才把请求转成持有记录。释放时更新记录，再调用实际的 unlock 或 up。

条件变量 wait 内部直接操作 mutex，因此也补充了对应记账：等待条件变量前登记释放，醒来后登记内部重新加锁请求，取得锁后登记持有。该内部请求只记账，不额外返回死锁错误，保留 wait 返回时持有 mutex 的语义。mutex 与 semaphore 分别检测，没有实现混合资源、waittid 等跨机制的完整依赖分析。
