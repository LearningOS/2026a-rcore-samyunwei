## 实验总结

本次实验迁移了 sys_get_time、mmap 和 munmap，适配新的进程结构，实现 spawn 直接从 ELF 创建子进程并建立父子关系。增加优先级与 stride 字段，实现 sys_set_priority，并在调度时选择 stride 最小的进程、累加对应步长。使用 u128 保存累计值，默认优先级为 16，初始 stride 为 0。

## 简答题

#### 进程创建

1、fork 后立即 exec 会丢弃刚复制的地址空间，有什么改进策略？

可以采用写时复制（Copy on Write）。fork 时让父子进程共享原有物理页，对原本可写的页面暂时取消写权限，并标记为写时复制。只有某一方真正写入时，才通过缺页异常分配新物理页并复制数据，再恢复写权限。这样子进程紧接着执行 exec 时，就不需要复制大部分旧页面。实现时还需要维护物理页引用计数，并区分写时复制页面与本来就只读的页面。

如果目的就是启动另一个程序，也可以直接使用 spawn。本次实现先翻译父进程传入的程序名，查找内置应用，再调用 TaskControlBlock::new，从目标 ELF 建立新的地址空间、用户栈、内核栈和执行现场。子进程通过 Weak 记录父进程，父进程通过 children 保存子进程的 Arc，最后将子进程加入就绪队列，并向父进程返回子 PID。程序名不存在时返回 -1。

本次没有实现写时复制。现有 fork 仍会复制用户页面；spawn 避开了这次复制，但底层创建进程时仍有分配失败触发断言或 unwrap 的路径，尚未统一转换为系统调用的 -1 返回值。

2、即使采用写时复制，fork 为什么仍然受到批评？（选做）

写时复制主要减少页面数据复制，无法消除 fork 继承整个进程状态的复杂性。多线程程序 fork 后，子进程只保留调用线程，却可能继承其他线程持有的锁，后续使用这些锁会死锁。页表和资源管理仍有开销，文件描述符、敏感数据等默认继承也增加了管理负担。GPU 等设备上的状态也很难随地址空间一起复制。这些问题说明，直接描述新进程所需资源的创建接口有其价值。[A fork() in the road](https://www.microsoft.com/en-us/research/uploads/prod/2019/04/fork-hotos19.pdf)

3、val 初始为 2，fork 前输出 0，父进程和子进程分别先运行时，输出是什么？

按题意忽略标准 I/O 缓冲，并将“先运行”理解为先执行到 wait 或进程结束。fork 后，父子进程各有一份 val，修改互不影响。

父进程先运行时，先输出 fork 前的 0，父进程将自己的 val 减为 1 并输出 1，然后在 wait 中等待。子进程将自己的 val 加为 3，输出 3，再加为 4 并输出 4 后退出。父进程等待结束后，将自己的 val 从 1 加为 2 并输出 2，最终结果为 01342。

子进程先运行时，先输出 fork 前的 0，子进程依次输出 3、4，父进程随后输出 1、2，最终结果为 03412。如果允许在这些输出之间抢占，还可能出现其他交错，但父进程最后的 2 一定在子进程退出后输出。

4、fork() && fork() && fork() || fork() && fork() || fork() && fork() 最后输出多少个 A？

假设所有 fork 都成功，并忽略标准 I/O 缓冲。&& 优先于 ||，表达式可以分成三个由 || 连接的组：三个 fork 的与运算、两个 fork 的与运算、两个 fork 的与运算。每次 fork 在父进程中返回正数，在子进程中返回 0，还要考虑逻辑运算的短路规则。

第一组最终产生 1 个结果为真的进程和 3 个结果为假的进程。为真的进程跳过后面两组，直接输出 A；3 个为假的进程继续计算第二组。

第二组中，每个进入的进程产生 1 个结果为真、2 个结果为假的进程，因此有 3 个进程跳过第三组并输出 A，另有 6 个进程进入第三组。

第三组中，每个进入的进程产生 3 个进程，真假结果都不影响后续 printf，因此产生 18 次输出。总数为 1 + 3 + 18 = 22 个 A。

对于任意 &&、|| 序列，可以按运算符优先级构建表达式树，每个节点记录结果为真和为假的进程数量。一个 fork 节点对应（1，1）。如果左右子树分别为（Lt，Lf）和（Rt，Rf），则 && 节点为（Lt × Rt，Lf + Lt × Rf），|| 节点为（Lt + Lf × Rt，Lf × Rf）。根节点的真假数量之和就是执行最后 printf 的进程数。

#### stride 调度

1、两个进程的 pass 都是 10，用 8 位无符号数保存 stride，p1 为 255、p2 为 250，p2 运行后实际会轮到 p1 吗？

如果直接按无符号数比较，并允许加法回绕，就不会轮到 p1。p2 的 stride 从 250 增加到 260，保存为 8 位无符号数后变成 4。普通比较会认为 4 小于 255，于是再次选择 p2。但按照未溢出的累计值，p1 的 255 小于 p2 的 260，应该选择 p1。在启用溢出检查的 Rust 运算中，普通加法还可能直接 panic，因此回绕比较必须配合显式的 wrapping_add 等运算。

2、为什么优先级都不小于 2 时，STRIDE_MAX - STRIDE_MIN 不超过 BigStride / 2？

考虑固定的一组进程，初始 stride 都是 0，并且每次都选择最小值进行更新。由于 priority >= 2，每次增加的 pass 不超过 BigStride / 2。

假设更新前最小值是 m，所有进程的 stride 都处于 [m, m + BigStride / 2]。本次只把一个最小值 m 增加不超过 BigStride / 2，它仍然处于这个区间；其他值不变，所以更新后的最大值与最小值之差仍不超过 BigStride / 2。初始情况满足这个条件，因此可以逐次保持。

这个推理依赖上述前提。运行中加入 stride 为 0 的新进程，不能直接假定仍然满足同样的界限。只修改优先级、始终保持 priority >= 2 且不重置 stride 时，每次步长仍不超过 BigStride / 2，不会单独破坏这个界限。

3、如何实现考虑溢出的 partial_cmp，并让 BinaryHeap 弹出逻辑上最小的 stride？

在两个累计值的真实距离小于计数空间一半的前提下，可以用回绕减法判断先后。对于 u64，将 wrapping_sub 得到的差转换为 i64，负数表示 self 在逻辑上更小，正数表示 self 更大。

Rust 的 BinaryHeap 默认弹出最大元素，所以为了弹出 stride 最小的进程，需要将逻辑比较结果反转。题目中的函数可以写为：

```rust
fn partial_cmp(&self, other: &Self) -> Option<Ordering> {
    let delta = self.0.wrapping_sub(other.0) as i64;
    Some(delta.cmp(&0).reverse())
}
```

这个方法要求累计值之间的距离严格小于 2^63；差值恰好为半个计数空间时无法区分先后。若实际使用 BinaryHeap，还需要提供与这个比较规则一致的 Ord、PartialEq 和 Eq 实现。题目代码中的 PartialEq for Person 应为 PartialEq for Stride。

本次内核采用 VecDeque 扫描最小值，没有使用 BinaryHeap，也没有使用上面的回绕比较器。内核将 stride 和 BIG_STRIDE 定义为 u128，BIG_STRIDE 取 2^64，使 isize::MAX 这样的合法优先级仍能得到正步长。每次 fetch 选择最小 stride 的进程，移出队列后增加一次步长，再交给 Processor 执行；进程让出 CPU 时保留累计值并重新入队。这个实现增大了数值范围，但没有从根本上解决长期运行的累计溢出问题。
