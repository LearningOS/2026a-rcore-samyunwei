## 简答题

#### 第六章：文件系统

1、在 easy-fs 中，root inode 起着什么作用？如果其中的内容损坏了，会发生什么？

root inode 是根目录对应的 inode，编号固定为 0。文件系统创建时首先分配并初始化它，打开文件系统时则根据超级块中的布局信息定位它。root inode 记录根目录的类型、大小和目录数据块的位置；目录数据块中保存文件名到 inode 编号的对应关系。当前 easy-fs 的文件都放在根目录，内核通过 ROOT_INODE 查找、创建和列出文件，也通过它找到需要加载的用户程序。

如果 root inode 的类型、大小或块索引损坏，内核就可能无法正确读取目录项，表现为文件找不到、目录内容错误，或者在类型检查和块访问时失败。由于程序加载同样依赖根目录，严重时连初始进程都无法启动。但目录无法访问不等于所有文件内容已经被擦除，其他 inode 和数据块可能仍然存在，只是正常的文件名查找路径被破坏。恢复需要依靠备份或对剩余元数据进行检查重建；当前 easy-fs 没有实现日志恢复功能，不能保证自动修复。

#### 第七章：进程间通信

1、举出一个使用 pipe 的实际应用例子。

在 Linux 终端中，可以执行下面的命令统计文件的换行符数量，通常用作行数统计：

```sh
cat example.txt | wc -l
```

shell 创建管道，让 cat 的标准输出指向管道写端，让 wc 的标准输入指向管道读端。cat 读取文件并写入管道，wc 一边读取一边统计，因此不需要先把 cat 的输出保存为临时文件。严格来说，wc -l 统计的是换行符，文件末尾没有换行符的最后一行不会额外计入。

两个进程和 shell 都需要关闭各自不用的管道端点。只有所有写端都关闭，且缓冲区中的数据已经读完，读端才会读到 EOF；如果还保留着多余的写端引用，wc 就可能一直等不到输入结束。

2、多个进程互相通信时，如何避免为每一对进程分别建立管道？

可以设计由内核管理的消息邮箱。每个进程拥有一个接收队列，发送方通过目标进程标识投递消息，接收方从自己的邮箱取消息。这样每个进程只需要管理一个接收入口，多个发送方可以向同一个邮箱发送消息，邮箱数量随进程数增长，不需要建立两两连接。

发送接口接收目标进程标识、用户缓冲区和长度。内核检查目标是否存在、是否允许通信，以及源缓冲区是否可读，再把数据复制到内核消息队列。每条消息记录发送者、长度和内容，保留消息边界。接收接口检查目标缓冲区是否可写，再返回一条消息及其发送者；缓冲区不足时返回错误并保留消息，避免静默截断。

为了限制内存占用，需要设置单条消息大小和邮箱容量上限。邮箱为空时，接收进程可以进入等待队列，收到消息后被唤醒；邮箱已满时，发送方可以阻塞等待或选择非阻塞返回错误。进程退出时关闭邮箱、释放消息并唤醒相关等待者，使其获得明确的错误结果。目标标识还应区分进程的不同生命周期，避免 PID 被复用后把旧消息发给另一个进程。

以上是多进程通信机制的设计方案，本次 ch6 分支没有实现消息邮箱。

## 实现与测试说明

本次沿用现有磁盘 inode 布局，通过统计根目录中指向同一 inode 的目录项获取 nlink。创建硬链接只添加目录项，文件内容继续共享。删除目录项时先保存剩余条目，再回收目录原来的数据块和索引块，重新分配并写回剩余条目，使目录项保持连续。这个实现便于复用现有接口，但每次删除都需要遍历并重写目录，性能仍有改进空间。

文件回收还结合了 OPEN_INODE_COUNTS。每创建一个 OSInode 对象就登记一次，在其 Drop 中减少计数；fork 共享的是 Arc，因此不会误把某个继承 fd 的关闭当成整个文件对象销毁。最后一个名字被删除后，如果没有打开对象就立即回收，否则等最后一个对象销毁时再回收。回收顺序为释放数据块及索引块，再归还 inode 位图中的编号。
